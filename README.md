# rust_multi_ranking_engine

> **여러 축의 점수를 스케일 안전하게 융합하고, 집합 제약 아래에서 상위 K개를 고르며,
> 탈락 사유까지 남기는 결정적 러스트 엔진.**

후보가 수백만 개이고 고를 것이 수십 개일 때, 무엇을 고를지 정하는 계층을 담당한다.
후보는 문서일 수도, 보안 이벤트일 수도, 유전자 돌연변이일 수도 있다. 엔진은 후보가 무엇인지 모른다.

**이 문서는 설계서다.** 2026년 8월 현재 구현된 코드는 없다. 아래 내용은 확정된 설계이지
동작하는 코드가 아니며, 무엇이 구현됐고 무엇이 아닌지는 [11. 개발 로드맵](#11-개발-로드맵)에
세 단계(동작 확인 / 코드만 존재 / 미구현)로 기록한다.

**핵심 참고 자료**

1. G. L. Nemhauser, L. A. Wolsey, M. L. Fisher, An analysis of approximations for maximizing submodular set functions (1978) - 서브모듈러 목적함수에서 탐욕 선택이 `1 - 1/e` 를 보장한다는 고전 결과
2. G. V. Cormack et al., Reciprocal Rank Fusion outperforms Condorcet and individual Rank Learning Methods, SIGIR 2009 - https://plg.uwaterloo.ca/~gvcormac/cormacksigir09-rrf.pdf
3. A. Clauset, C. R. Shalizi, M. E. J. Newman, Power-law distributions in empirical data (2009) - 멱법칙 적합이 왜 틀리기 쉬운지, 적합도 검정이 왜 필요한지

두 번째가 점수 융합의 근거이고 첫 번째가 제약 아래 선택의 근거다. 세 번째는 이 엔진이

## 1. 왜 이 엔진인가

### 같은 것을 두 번 만들었다

이 프로젝트의 출발점은 새로운 아이디어가 아니라 **이미 두 번 손으로 만든 구조를 뒤늦게 알아본 것**이다.

한 자매 프로젝트는 여러 검색 소스의 결과를 하나의 순위로 합친다. 소스마다 점수 체계가 달라
값을 더할 수 없으므로 순위만 융합한다.

다른 자매 프로젝트는 텍스트 한 구간에 여러 개인정보 엔티티 후보를 붙이고, 검증식과 문맥과
정규화 비용으로 점수를 매기고, 엔티티별 등급 천장에 눌러 놓고, 부정 문맥이면 거부하고,
가장 높은 하나만 채택한 뒤 나머지를 사유와 함께 기록한다.

두 번째 것을 절차로 적으면 이렇게 된다.

```text
후보 생성      한 구간에 붙는 엔티티 후보들
다축 채점      검증식 통과 여부, 문맥 단서, 정규화 비용 감점
제약 적용      엔티티별 등급 천장, 최소 문맥, 부정 문맥 거부
선택           최고점 하나 (K = 1)
근거 기록      나머지는 탈락 사유와 함께 남긴다
```

**같은 골격이다.** 도메인만 다르다. 억지로 일반화한 것이 아니라 모르고 두 번 만든 것을
알아본 경우이고, 그것이 추상화가 실재한다는 가장 좋은 신호다.

### 러스트 쪽에 빈자리가 있다

2026년 8월 기준 crates.io 실측이다.

| 크레이트 | 버전 | 상태 |
| --- | --- | --- |
| `rerank` | 0.0.0 | 이름만 선점. 내용 없음 |
| `ltrs` | 0.0.0 | 이름만 선점. 내용 없음 |
| `rankit` | 0.1.7 | 학습 순위화(learning to rank) 손실함수와 평가지표만 |
| `adarank` | 0.1.0 | 알고리즘 하나 |
| `zen-engine` | 2.0.1 | 비즈니스 규칙 엔진. 랭킹 아님 |
| `rust-rule-engine` | 1.21.4 | RETE 규칙 엔진. 랭킹 아님 |

**`0.0.0` 이 둘이라는 것이 신호다.** 수요는 인지됐는데 아무도 채우지 않았다. 그리고 지금 있는 것은
전부 부품이다. 손실함수 하나, 알고리즘 하나, 규칙 엔진 하나. **점수 융합과 제약과 상위 K 선택과
감사를 한 흐름으로 묶은 것이 없다.**

## 2. 문제 정의

### 한 문장

많은 후보 중에서 여러 기준으로 점수를 매기고, 지켜야 할 제약을 걸어, 소수를 골라내고,
왜 골랐는지 남긴다.

### 세 줄로 안 되는 이유

코드로 쓰면 `candidates.sort_by_key(score).take(k)` 다. 그런데 실제 문제는 네 자리에서 갈라진다.

**첫째, 규모.** 후보가 1,000만이고 K가 30이면 정렬하면 안 된다. 전체 정렬 `O(N log N)` 대신
유계 힙으로 `O(N log K)` 다. 더 중요한 것은 **후보를 전부 메모리에 올리지 않는 것**이다.

**둘째, 점수를 더할 수 없는 경우.** 모델 A는 로짓을 내고 B는 확률을 내고 C는 0에서 100을 낸다.
단순 가중합은 여기서 조용히 틀린다. 로짓 하나가 다른 축 전부를 압도한다.

**셋째, 제약이 필터가 아닐 때.** 이것이 가장 어렵다.

| 종류 | 예시 | 판정 방법 |
| --- | --- | --- |
| 단항 제약 | 안전성 검사를 통과한 것만 | 후보 하나씩 보면 됨 |
| 집합 제약 | 34개를 고르되 같은 유전자에서 3개를 넘지 말 것 | 후보 하나씩 봐서는 불가능 |
| 집합 제약 | 총 토큰 예산 이하 | 후보 하나씩 봐서는 불가능 |

집합 제약이 걸리면 **상위 K개가 정답이 아니게 된다.** 점수 1위, 2위, 3위가 전부 같은 유전자면
그중 하나를 버리고 4위를 넣어야 한다.

**넷째, 목적함수가 후보별 독립이 아닐 때.** 검색 결과를 고를 때 실제 목표는 이런 모양이다.

```text
목표:  관련성(S) + 포괄성(S) + 연결성(S) - 중복성(S)  을 최대화
       S 는 고를 후보 집합
제약:  토큰비용(S) <= 예산
```

관련성과 연결성은 후보별로 계산되지만 **포괄성과 중복성은 집합 전체의 함수**다. 세 번째 문서의
가치는 앞의 둘이 무엇이었느냐에 달려 있다.

### 이것은 NP-hard 계열이다

집합 제약 아래 부분집합 선택은 일반형이 NP-hard 다. 이 엔진의 일은 그것을 푸는 것이 아니라
**어느 경우인지 판별해서 맞는 알고리즘을 고르고, 근사일 때는 근사라고 말하는 것**이다.

| 목적함수 | 제약 | 최적성 | 전략 |
| --- | --- | --- | --- |
| 모듈러(가산) | 없음 또는 개수 제한 | 상위 K가 최적 | 유계 힙 |
| 모듈러 | 분할 매트로이드 (그룹당 최대 m개) | 탐욕이 정확히 최적 | 탐욕과 그룹 카운터 |
| 모듈러 | 배낭형 (총 예산) | NP-hard | 탐욕 근사 또는 소규모 동적계획 |
| 서브모듈러 | 개수 제한 | NP-hard | 탐욕이 `1 - 1/e`(약 0.632) 보장 |
| 서브모듈러 | 배낭형 | NP-hard | 근사, 보장 계수를 함께 보고 |

**충분히 좋은 해와 남은 오차의 명시가 여기서 기능이 된다.** 근사인 것을 아는 정도가 아니라
얼마나 근사인지를 결과에 실어 보낸다.

## 3. 설계 원칙

### 정렬이 아니라 선택이다

이 엔진은 순위표를 만드는 것이 목적이 아니라 **고르는 것**이 목적이다. 그래서 이름은 랭킹이지만
반환값의 중심은 선택된 집합과 그 근거다.

### 틀리기 쉬운 것을 못 하게 만든다

로짓과 확률을 섞어 더하는 것은 흔한 실수다. 엔진은 그것을 문서로 경고하는 대신 **거부한다**.
채점기가 자기 점수의 척도를 선언하게 하고, 비교 불가능한 척도에 가중합을 걸면 오류를 낸다.

### 조용히 사라지는 후보가 없다

모든 후보는 결과에 들어가거나 사유와 함께 기록되거나 둘 중 하나다. 중간은 없다.
탈락 사유 출력은 부가 기능이 아니라 이 엔진이 규제 도메인에서 쓰일 수 있는 최소 요건이다.

### 결정적이다

같은 입력이면 스레드 수와 무관하게 같은 출력이 나온다. 동점 처리 순서까지 같다.
그래야 캐싱과 테스트와 감사 추적이 성립한다.

### 모델을 부르지 않는다

엔진은 신경망을 실행하지 않는다. 채점기는 트레잇이고 그 안에서 무엇을 부를지는 호출자의 몫이다.
기본 빌드는 순수 러스트이며 외부 함수 인터페이스(FFI, Foreign Function Interface) 호출이 없다.

## 4. 아키텍처

### 두 단계로 나뉘는 이유

스트리밍과 집합 제약은 근본적으로 충돌한다. 집합 제약을 보려면 후보 풀이 있어야 하는데
스트리밍은 풀을 만들지 않는 것이 목적이다. 그래서 나눈다.

```text
1단계 (스트리밍)
  후보 N개 → 싼 채점기 → 단항 제약 → 유계 힙 상위 M개
             M = K 곱하기 배수 (기본 32배, 조정 가능)
             메모리 O(M), 시간 O(N log M)

2단계 (풀 위에서)
  상위 M개 → 비싼 채점기 → 집합 제약 아래 선택 → 최종 K개
             매트로이드면 탐욕이 정확, 아니면 근사와 보장 계수 보고
```

### 이것은 근사이고 그 사실을 숨기지 않는다

M 밖으로 밀려난 후보가 집합 제약 때문에 최종 해에 들어가야 했을 수 있다. 그래서 결과에 싣는다.

| 필드 | 의미 | 위험 신호 |
| --- | --- | --- |
| `pool_size` | 1단계가 남긴 M | |
| `pool_exhausted` | 풀을 다 쓰고도 K를 못 채웠다 | 참이면 M을 키워야 한다 |
| `exact` | 매트로이드라 탐욕이 최적이었다 | |
| `guarantee` | 근사 보장 계수 (예: 0.632) | `exact` 가 거짓일 때만 |

조용히 부족한 답을 주는 대신 말한다.

### 채점기 비용에 따라 단계를 나눈다

채점기 하나가 다른 것보다 1,000배 비싸면 모든 후보에 다 돌리는 것은 설계 결함이다.
검색 시스템에서 캐스케이드 순위화라 부르는 방식을 쓴다.

```text
후보 N개 → 싼 채점기 → 상위 M개 → 비싼 채점기 → 상위 K개
```

비싼 채점기가 몇 번 불렸는지도 감사 기록에 남긴다. 그래야 비용을 되짚을 수 있다.

### 엔진의 경계

특징 계산은 엔진 밖이다. 그래프 라플라시안 고유벡터나 임베딩은 색인 시점에 미리 구해 두고,
엔진은 그 좌표를 점수 축 하나로 받아 쓸 뿐이다.

| 엔진 밖 (색인 시점) | 엔진 안 (질의 시점) |
| --- | --- |
| 임베딩 생성 | 받은 축들을 융합 |
| 그래프 중심성, 스펙트럴 좌표 | 제약 적용 |
| 커뮤니티 탐지 | 예산 안에서 선택 |
| 모델 학습 | 근거 기록 |

엔진에 고유값 분해나 모델 학습을 넣지 않는다. 그것은 다른 물건의 일이다.

## 5. 공통 타입

### 점수와 결과

```rust
/// 후보 하나가 받은 점수 전부. 융합 전 원본을 보관한다.
pub struct ScoreSet {
    values: Vec<(ScorerId, Option<f32>)>,
}

/// 최종 결과. 왜 이 순위인지 재현 가능해야 한다.
pub struct Ranked<C> {
    pub candidate: C,
    pub rank: u32,
    pub fused: f32,
    pub scores: ScoreSet,        // 융합 전 원본
    pub fusion: FusionTrace,     // 어떻게 합쳤는가
}

/// 떨어진 후보.
pub struct Rejected<C> {
    pub candidate: C,
    pub reason: RejectReason,
    pub fused: Option<f32>,
}

pub enum RejectReason {
    /// 채점기가 값을 내지 못했다. 0점과 다르다.
    NotScored(ScorerId),
    /// 단항 제약에 걸렸다.
    UnaryConstraint(ConstraintId),
    /// 집합 제약 때문에 자리를 못 얻었다.
    SetConstraint(ConstraintId),
    /// 점수가 문턱 아래다.
    BelowThreshold,
    /// 더 높은 후보에게 밀렸다.
    Outranked,
    /// 1단계 풀에 들지 못했다.
    OutOfPool,
}
```

### 채점 불가와 0점은 다르다

`Option<f32>` 가 중요하다. 모델이 돌지 않았는데 0점으로 세면 그 후보는 부당하게 죽는다.
융합 단계는 값이 없는 축을 만나면 세 가지 중 하나를 택하고 어느 것을 택했는지 기록한다.

| 정책 | 동작 | 언제 |
| --- | --- | --- |
| `Skip` | 그 축을 빼고 나머지로 융합. 가중치를 재정규화 | 축이 선택적일 때 |
| `Impute(v)` | 지정한 값으로 대체 | 결측이 의미를 갖는 경우 |
| `Reject` | 후보를 `NotScored` 로 탈락 | 필수 축일 때 |

## 6. 트레잇 표면

트레잇은 둘이면 된다. 나머지는 사용자가 구현할 것이 아니라 엔진이 제공하는 구체 타입이다.

```rust
pub trait Candidate {
    fn id(&self) -> CandidateId;
}

pub trait Scorer<C: Candidate>: Sync {
    fn id(&self) -> ScorerId;

    /// 이 점수가 어떤 척도인가. 융합 가능성 판정에 쓰인다.
    fn scale(&self) -> ScoreScale;

    /// 얼마나 비싼가. 캐스케이드 단계 배치에 쓰인다.
    fn cost(&self) -> ScorerCost;

    fn score(&self, c: &C) -> Option<f32>;
}
```

사용자가 확장하는 것은 **후보가 무엇인가**와 **어떻게 점수를 매기는가** 둘뿐이다.
융합 방식, 선택 알고리즘, 근거 기록은 엔진의 일이므로 트레잇으로 열지 않는다.

### 빌더

```rust
let out = Engine::new()
    .scorer(semantic_relevance)      // 싼 축
    .scorer(recency)                 // 싼 축
    .scorer(cross_encoder)           // 비싼 축. 2단계로 밀린다
    .fuse(Fusion::Rrf { k: 60.0 })
    .unary(min_authority(0.3))
    .set_constraint(max_per_source(3))
    .budget(Budget::TopK(30))
    .run(candidates)?;

out.ranked       // Vec<Ranked<C>>
out.rejected     // Vec<Rejected<C>>
out.selection    // 정확해였는가, 보장 계수, 풀 소진 여부
out.trace        // 채점기별 호출 횟수와 소요 시간
```

## 7. 점수와 융합

### 척도를 선언하게 한다

```rust
pub enum ScoreScale {
    /// 0 이상 1 이하. 확률이나 정규화된 값. 서로 더해도 된다.
    Unit,
    /// 로짓이나 거리. 정규화 없이 더하면 틀린다.
    Unbounded,
    /// 순서만 의미가 있다. 값끼리 더할 수 없다.
    Rank,
}
```

엔진은 이 선언을 근거로 융합 가능성을 판정한다.

| 융합 방식 | `Unit` 만 | `Unbounded` 포함 | `Rank` 포함 |
| --- | --- | --- | --- |
| `WeightedSum` | 허용 | 거부. 정규화를 먼저 걸어야 한다 | 거부 |
| `Rrf` | 허용 | 허용. 순위만 쓴다 | 허용 |
| `Max` | 허용 | 거부 | 거부 |

`Unbounded` 축을 가중합에 넣으려면 정규화기를 명시적으로 끼워야 한다.

```rust
.scorer(logit_model.normalized(Normalizer::Sigmoid))
```

거부는 실행 시점 오류가 아니라 **빌더 단계 오류**다. 후보를 한 건도 처리하기 전에 걸린다.

### 순위 융합을 기본값으로 둔다

축이 서로 다른 곳에서 왔다면 값을 더하는 것보다 순위를 합치는 편이 안전하다.

```text
RRF(d) = 각 소스에 대해 1 / (k + 순위(d)) 를 더한 값
```

`k` 는 상위 순위의 영향력을 조절한다. 값이 크면 순위 차이가 완만해진다.

### 결정성을 지키는 방법

채점은 병렬로 하되 **융합은 후보 식별자 순으로 고정 순서 합산**한다.
부동소수 덧셈은 결합법칙이 성립하지 않으므로, 합산 순서가 스레드 스케줄에 따라 달라지면
값이 미세하게 갈리고 동점 처리가 뒤집힌다. 이것을 지키지 않은 병렬 순위화 코드가 흔하다.

동점일 때는 후보 식별자 오름차순으로 정렬한다. 임의 순서를 남기지 않는다.

## 8. 제약과 목적함수

### 두 종류의 제약

```rust
pub trait UnaryConstraint<C> {
    fn id(&self) -> ConstraintId;
    fn allows(&self, c: &C) -> bool;
}

pub trait SetConstraint<C> {
    fn id(&self) -> ConstraintId;
    /// 이 후보를 현재 선택에 더할 수 있는가.
    fn admits(&self, selected: &[&C], candidate: &C) -> bool;
    /// 매트로이드 구조인가. 참이면 탐욕이 최적임을 보장할 수 있다.
    fn is_matroid(&self) -> bool;
}
```

`is_matroid` 를 구현자가 선언하게 하는 것은 위험해 보이지만 의도적이다. 임의의 제약이
매트로이드인지 엔진이 자동으로 판정할 수는 없다. 대신 **엔진이 기본 제공하는 제약은
그 성질이 증명된 것만** 둔다.

| 기본 제공 제약 | 매트로이드 | 보장 |
| --- | --- | --- |
| `max_per_group(key, m)` | 예 (분할 매트로이드) | 탐욕이 정확 |
| `max_total(k)` | 예 (균일 매트로이드) | 탐욕이 정확 |
| `budget(cost_fn, limit)` | 아니오 (배낭형) | 근사 |
| `require_at_least(pred, n)` | 아니오 | 근사, 실현 가능성 검사 필요 |

사용자가 직접 구현하면서 `is_matroid` 를 참으로 잘못 선언하면 보장이 깨진다.
그래서 결과의 `exact` 는 엔진이 그렇게 선언받았다는 뜻이지 엔진이 증명했다는 뜻이 아니다.

### 집합 목적함수

후보별 독립 점수의 합이 아닌 목적함수를 지원한다.

```rust
pub trait SetObjective<C> {
    /// 현재 선택에 이 후보를 더했을 때의 이득.
    fn marginal_gain(&self, selected: &[&C], candidate: &C) -> f32;
    /// 서브모듈러인가. 참이면 탐욕에 1 - 1/e 보장이 붙는다.
    fn is_submodular(&self) -> bool;
}
```

포괄성과 중복성이 여기 들어간다. 이미 비슷한 문서를 골랐다면 다음 문서의 한계 이득은 줄어든다.
그것이 서브모듈러의 정의다.

목적함수를 주지 않으면 기본값은 모듈러(융합 점수의 합)이고 그때는 상위 K가 최적이다.

## 9. 선택 예산

### K를 상수로 두지 않는다

정보가 몇 군데 몰려 있으면 K는 작아야 하고 넓게 퍼져 있으면 커야 한다.
고정 K는 두 경우 모두에서 틀린 값이다.

```rust
pub enum Budget {
    /// 고정 개수.
    TopK(u32),
    /// 누락 허용 질량으로 K를 유도한다.
    TailMass { epsilon: f32 },
    /// 비용 예산. 배낭형 제약이 된다.
    Tokens { max: u32 },
}
```

### 꼬리 질량으로 K를 유도하는 방법

접근 빈도가 긴 꼬리 분포를 보이는 경우가 많다. 순위 `r` 인 항목의 확률을 `r` 의 `-s` 승으로
근사하면 상위 K개 뒤에 남는 질량을 계산할 수 있고, 허용 누락 `epsilon` 을 만족하는
최소 K를 찾을 수 있다.

후보 수가 유한하므로 무한합이 아니라 **절단 조화합**을 쓴다. 지수가 1에 가까우면
무한합이 발산하기 때문이다.

```rust
/// 특수함수 라이브러리가 필요 없다. 합 두 개다.
fn tail_mass(s: f32, k: usize, v: usize) -> f32 {
    let head: f32 = (1..=k).map(|r| (r as f32).powf(-s)).sum();
    let all: f32 = (1..=v).map(|r| (r as f32).powf(-s)).sum();
    1.0 - head / all
}
```

같은 값이 캐시 크기 결정에도 쓰인다. 적중률은 위 식의 여집합이다.
추정한 지수 하나가 검색 예산과 캐시 크기를 동시에 정한다.

### 적합도를 재지 않으면 쓰지 않는다

이 방식 전체가 지수 `s` 의 추정에 걸려 있다. 멱법칙 적합은 틀리기 쉽기로 유명하다.
로그 축에서 직선처럼 보이는 것과 실제로 멱법칙인 것은 다르다. 멱법칙이 아닌 분포에
멱법칙을 맞추면 **자신 있게 틀린 K** 가 나온다.

```rust
pub struct BudgetTrace {
    pub s: f32,
    pub fit_quality: f32,     // 적합도
    pub fallback: bool,       // 적합이 나빠 고정 K로 되돌렸는가
    pub derived_k: u32,
}
```

적합이 문턱에 못 미치면 유도된 K를 버리고 고정 K로 되돌리며 그 사실을 기록한다.
가정하고 쓰는 것이 아니라 재고 나서 쓴다.

## 10. 불변식과 품질 신호

### 불변식 넷

정확성을 문장이 아니라 검사로 못박는다. 테스트가 이것을 강제한다.

| 불변식 | 내용 | 검증 방법 |
| --- | --- | --- |
| **결정성** | 같은 입력이면 스레드 수와 무관하게 순위와 동점 처리까지 동일 | 1스레드 결과와 다중 스레드 결과를 비교 |
| **완전성** | 모든 후보가 결과 또는 탈락 목록에 정확히 한 번 나타난다 | 두 목록의 길이 합이 입력 수와 같은지 확인 |
| **제약 준수** | 반환된 집합이 선언된 집합 제약을 전부 만족한다 | 결과를 제약에 다시 통과시킨다 |
| **근거 재현** | 원본 점수와 융합 기록만으로 최종 점수를 다시 계산할 수 있다 | 재계산 후 비교 |

결정성이 가장 까다롭다. 병렬 채점에서 부동소수 합산 순서가 흔들리면 값이 갈리고
동점 처리가 뒤집힌다. 고정 순서 합산과 결정적 동점 규칙으로 막는다.

### 절단선의 여유

K번째와 K+1번째의 점수 차가 거의 0이면 그 선택은 흔들린다. 씨앗이나 부동소수 오차 하나로
순위가 뒤집힌다. **34개를 골랐다는 것과 34번째와 35번째가 사실상 같았다는 것은 다른 사건이다.**

```rust
pub struct Selection {
    pub exact: bool,
    pub guarantee: Option<f32>,
    pub pool_size: u32,
    pub pool_exhausted: bool,
    pub cut_margin: Option<f32>,    // K번째 점수에서 K+1번째 점수를 뺀 값
}
```

계산 비용은 사실상 0이다. 이미 힙에 있는 두 값의 차다.

`cut_margin` 과 `Budget::TailMass` 는 한 쌍이다. 하나는 절단선 바로 옆을 보고
다른 하나는 꼬리 전체를 본다. 둘 다 K를 옳은 자리에서 잘랐는가를 묻는다.

### 감사 출력

결과 하나를 JSON 으로 내면 이런 모양이다.

```json
{
  "candidate": "doc-3141",
  "rank": 3,
  "fused": 0.913,
  "scores": {
    "semantic": 0.94,
    "centrality": 0.87,
    "recency": null
  },
  "missing_policy": "skip",
  "fusion": { "method": "rrf", "k": 60.0 },
  "constraints": { "max_per_source": "pass" }
}
```

`recency` 가 값 없음이고 정책이 건너뛰기였다는 것까지 남는다.
왜 3위인가에 답할 수 있어야 규제 도메인에서 쓸 수 있다.

## 11. 개발 로드맵

상태는 세 가지로만 표기한다. **동작 확인**은 실제로 실행해 결과를 본 것이고,
**코드만 존재**는 작성됐으나 검증되지 않은 것이며, **미구현**은 아직 없는 것이다.

| 단계 | 산출물 | 검증 수단 | 상태 |
| --- | --- | --- | --- |
| 0 | 설계 확정 (이 문서) | | 완료 |
| 1 | 공통 타입, 트레잇, 스트리밍 유계 힙 | 결정성과 완전성 불변식 테스트 | 미구현 |
| 2 | 융합 세 방식과 척도 판정 | 비교 불가 척도 거부 테스트 | 미구현 |
| 3 | 단항 제약, 집합 제약, 매트로이드 탐욕 | 제약 준수 불변식 테스트 | 미구현 |
| 4 | 집합 목적함수, 서브모듈러 탐욕과 보장 계수 | 최적해를 아는 소규모 사례와 비교 | 미구현 |
| 5 | 적응형 예산과 적합도 검정 | 합성 분포로 유도 K 검증 | 미구현 |
| 6 | 감사 출력, 근거 재현 검사 | 근거 재현 불변식 테스트 | 미구현 |
| 7 | Python 바인딩 | Python 회귀 테스트 | 미구현 |

### 첫 검증 대상

자매 프로젝트의 순위 융합 함수를 이 엔진으로 대체할 수 있는지가 추상화의 시험대다.

이유가 셋이다. 실제로 도는 코드이고 테스트가 붙어 있어 **결과가 같은지 바로 검증**된다.
범위가 작아 며칠이면 판정이 난다. 그리고 **못 하면 추상화가 틀린 것이다.**
50줄짜리 기존 함수를 깨끗이 흡수하지 못하는 범용 엔진은 더 큰 곳에서도 안 된다.

이 관문을 통과한 뒤에 검색 증강 생성(RAG, Retrieval Augmented Generation) 파이프라인으로 넘어간다.

## 14. 알려진 한계

### 구조적으로 남는 것

**두 단계 분할은 근사다.** 1단계 풀 밖으로 밀려난 후보가 집합 제약 때문에 최종 해에
들어가야 했을 수 있다. `pool_exhausted` 로 신호를 보내지만 신호가 없다고 최적이 보장되지는 않는다.

**매트로이드 선언은 신뢰에 의존한다.** 사용자가 직접 구현한 제약의 성질을 엔진이 증명할 수 없다.
잘못 선언하면 `exact` 가 참인데 실제로는 최적이 아닐 수 있다. 기본 제공 제약만 쓰면 이 위험이 없다.

**적응형 예산은 분포 가정에 걸려 있다.** 접근 패턴이 멱법칙이 아니면 유도된 K가 틀린다.
적합도 검정으로 걸러내지만 검정 자체도 표본이 적으면 신뢰도가 떨어진다.

### 이 엔진이 필요 없는 경우

정직하게 적어 둔다. 다음 경우에는 이 엔진을 쓰지 않는 편이 낫다.

- 후보 수가 K보다 조금 많은 정도일 때. 그냥 정렬하면 된다
- 점수 축이 하나뿐일 때. 융합할 것이 없다
- 집합 제약이 없을 때. 상위 K가 이미 최적이다
- 병목이 선택이 아니라 그 뒤의 생성 단계일 때

엔진이 이것을 감지하면 결과에 표시한다. 자기가 필요 없는 자리라고 말할 수 있어야 한다.

## 15. 디렉토리 구조

현재 존재하는 것은 굵게 표시했다. 나머지는 계획이다.

- **`README.md`** 이 문서
- `Cargo.toml` 패키지와 기능 플래그
- `LICENSE`
- `src/`
  - `lib.rs` 공개 API 진입점
  - `candidate.rs` 후보 식별자
  - `score.rs` 채점기 트레잇, 척도, 점수 집합
  - `fuse.rs` 융합 방식과 융합 기록
  - `constraint.rs` 단항 제약, 집합 제약, 매트로이드 판정
  - `objective.rs` 집합 목적함수와 한계 이득
  - `budget.rs` 예산 정책과 적합도 검정
  - `select.rs` 스트리밍 유계 힙, 제약 아래 선택
  - `evidence.rs` 결과와 탈락 사유, 감사 출력
  - `engine.rs` 빌더와 오케스트레이션
- `tests/` 불변식 테스트
- `benches/` 규모별 처리량 측정
- `examples/` 실행 가능한 예제

단일 크레이트로 시작한다. 크레이트를 미리 쪼개면 서로를 부르는 배관만 늘어난다.
실제로 갈라야 할 이유가 생기면 그때 나눈다.
